## 1. XXD

Der Befehl `xxd` sorgt dafür das eingegebene Normale Buchstaben in Asc Code angezeigt werden.

bsp:
```sh
echo "a" | xxd
00000000: 610a                                     a.
```

### Die Optionen `-n -r -p` 

-n sorgt dafür das echo keinen Zeilenumbruch mehr dranhängt.

-p sorgt dafür das xxd nur mehr der Ascii Code angezeigt wird und nicht mehr die Stelle wo es liegt in Hex und was es in Normalen Zeichen ist.

-r sorgt dafür das xxd rückwärts funktionert also aus Ascci normale Zeichen macht.


bsp mit Emojis:

```sh
echo -n "😃" | xxd -p
f09f9883
```


```sh
echo -n "f09f9883" | xxd -r -p
😃
```

### Aufgabe: Hex Dump

**Aufgabenstellung:** Zeige mit `xxd` und `hexdump` eine binäre Ausgabe an (`-b` Option).

**Lösung:**

Mit `xxd -b` wird jedes Byte als 8 Bits (Binär) dargestellt:

```sh
echo -n "A" | xxd -b
00000000: 01000001                                               A
```

Mit `hexdump -b` wird stattdessen jedes Byte als Oktalwert ausgegeben:

```sh
echo -n "A" | hexdump -b
0000000 101
0000001
```

Der Unterschied: `xxd -b` zeigt echte Binärdarstellung, `hexdump -b` zeigt Oktal.

### Aufgabe: Octet

**Aufgabenstellung:** Was bedeutet „Octet" und warum wird es verwendet?

**Lösung:**

Ein **Octet** ist eine Einheit aus genau 8 Bit. Der Begriff entstand, weil früher nicht jedes System ein Byte mit 8 Bit definierte – es gab Architekturen mit 6, 7 oder 9 Bit pro Byte. Um Missverständnisse in der Netzwerkkommunikation zu vermeiden, wurde der Begriff „Octet" eingeführt, der eindeutig immer 8 Bit meint. Heute ist ein Byte zwar standardmäßig 8 Bit, aber in Protokollen wie IPv6 oder MIME wird „Octet" weiterhin als präziserer Begriff genutzt.

### Aufgabe: xxd Option `-E`

**Aufgabenstellung:** Was bewirkt die Option `-E` bei `xxd`?

**Lösung:**

Die Option `-E` schaltet die Zeichenanzeige rechts im xxd-Output von ASCII auf **EBCDIC** um. EBCDIC (Extended Binary Coded Decimal Interchange Code) ist ein älterer Zeichensatz von IBM, der vor allem auf Großrechnern (Mainframes) der 60er und 70er Jahre verwendet wurde. Die Reihenfolge der Zeichen unterscheidet sich stark von ASCII.

```sh
echo -n "Hello" | xxd -E
00000000: 4865 6c6c 6f                             &#$%%
```

Praktisch relevant ist das heute nur noch bei der Arbeit mit alten IBM-Systemen oder beim Lesen von Daten, die auf Mainframes erzeugt wurden.

### Aufgabe: Printf und `%.8x`

**Aufgabenstellung:** Erkläre `printf "%.8x"` und wie man einen Hex-Wert zurück in Dezimal umrechnet.

**Lösung:**

`printf "%.8x"` gibt eine Zahl als Hexadezimalwert aus, aufgefüllt auf 8 Stellen mit führenden Nullen:

```sh
printf "%.8x\n" 65
00000041
```

Das Zeichen `A` hat den Dezimalwert 65, was in Hex `41` ergibt.

Für einen Unicode-Codepoint wie 😃 (Dezimal: 128515):

```sh
printf "%.8x\n" 128515
0001f603
```

**Rückkonvertierung** von Hex nach Dezimal geht mit der Shell-Syntax `$((16#...))`:

```sh
echo $((16#41))
65

echo $((16#c39f))
50079
```

### Aufgabe: Windows Editor – UTF-8 vs. ANSI

**Aufgabenstellung:** Was ist der Unterschied zwischen UTF-8 und ANSI im Windows Editor, und welche Kodierung ist Standard?

**Lösung:**

Im Windows-Editor (Notepad) kann beim Speichern die Kodierung gewählt werden:

- **UTF-8**: Sonderzeichen wie `ä`, `ö`, `ü`, `€` oder Emojis werden korrekt gespeichert, da UTF-8 alle Unicode-Zeichen abdeckt.
- **ANSI**: Verwendet eine regionale Codepage (z. B. Windows-1252 für Westeuropa). Zeichen außerhalb dieser Codepage (z. B. Emojis, asiatische Schriftzeichen) werden falsch oder gar nicht gespeichert.

Seit **Windows 10** speichert Notepad standardmäßig in **UTF-8 ohne BOM**. Ältere Versionen verwendeten ANSI als Standard, was häufig zu Problemen bei der Weitergabe von Dateien geführt hat.

### Aufgabe: Hexdump Analyse – ANSI vs. UTF-8

**Aufgabenstellung:** Zeige die Kodierung von `Ö`, `ß` und `€` in ANSI (Windows-1252) und UTF-8 per Hexdump.

**Lösung:**

| Zeichen | ANSI (Windows-1252) | UTF-8 |
|---------|---------------------|-------|
| Ö | `d6` | `c396` |
| ß | `df` | `c39f` |
| € | `80` | `e282ac` |

In ANSI belegt jedes dieser Zeichen nur **1 Byte**, aber die Werte sind proprietär und nur innerhalb der jeweiligen Codepage gültig. In UTF-8 belegen `Ö` und `ß` jeweils **2 Bytes**, `€` sogar **3 Bytes** – dafür ist die Kodierung weltweit eindeutig.

Beispiel UTF-8 Überprüfung in der Shell:

```sh
echo -n "Ö" | xxd -p
c396

echo -n "ß" | xxd -p
c39f

echo -n "€" | xxd -p
e282ac
```

### Aufgabe: Zeilenumbrüche – Windows vs. Linux

**Aufgabenstellung:** Was ist der Unterschied zwischen Zeilenumbrüchen unter Windows und Linux?

**Lösung:**

Zeilenumbrüche werden je nach Betriebssystem unterschiedlich kodiert:

| System | Kürzel | Hex | Bedeutung |
|--------|--------|-----|-----------|
| Linux / macOS | `LF` | `0a` | Line Feed |
| Windows | `CR LF` | `0d 0a` | Carriage Return + Line Feed |

Windows verwendet zwei Steuerzeichen: zuerst `CR` (Wagenrücklauf, `0d`), dann `LF` (Zeilenvorschub, `0a`). Linux nutzt nur `LF`.

Das kann zu Problemen führen, wenn eine Windows-Datei unter Linux geöffnet wird – dann erscheint am Zeilenende ein `^M` (sichtbares `CR`).

Überprüfung mit xxd:

```sh
printf "Zeile1\r\nZeile2" | xxd -p
5a65696c65310d0a5a65696c6532
```

Das `0d0a` in der Mitte zeigt den Windows-Zeilenumbruch. Unter Linux wäre es nur `0a`.
